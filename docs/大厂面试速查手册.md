# OnCall Agent 大厂面试速查手册

> 使用方法：先记住第 1～4 节，再按目标岗位学习对应问答。  
> 回答原则：先说结论，再说设计，再说取舍，最后主动说明当前边界和下一步。

## 1. 30 秒项目介绍

> 我实现了一个面向标准化运维事故的 OnCall Agent。系统接收并去重告警，通过只读工具网关收集指标、日志、Trace 和变更证据，结合规则引擎、DeepSeek 和分层 Hybrid RAG 生成可验证的根因假设。后续通过版本化 Runbook、风险门控、人工审批、恢复验证、失败回滚和知识审核形成闭环。公开部署只使用 Dry Run，没有让模型直接持有生产写权限。

## 2. 2 分钟项目介绍

> 这个项目解决的是值班过程中大量高频、标准化但重复的调查工作。传统流程需要人工在告警、日志、指标、链路、变更和 Runbook 之间切换，确认慢且经验难沉淀。
>
> 系统有三条核心链路。第一条是事故链路：接收企业 Webhook 或 Wikimedia 真实公开事故，根据 fingerprint 去重，然后创建 Agent Run。第二条是调查链路：固定只读网关并行查询指标、日志、Trace 和变更，系统把观察事实、根因假设和处置建议分开；DeepSeek 不可用时会退化到确定性规则。第三条是控制链路：建议必须匹配版本化 Runbook，经过风险门控和人工审批，公开环境只执行非生产演练，然后验证恢复、失败回滚并生成待审核复盘。
>
> 知识库采用 BM25、多语言向量和 RRF 融合。Runbook、历史事故、实时状态、组件官方文档和外部企业复盘分别放在不同命名空间，并按照权威度和问题意图重排，避免外部类比直接生成生产操作。
>
> 当前项目是完整的控制面原型，不是已经接管生产的自动修复系统。生产化还需要 SSO/RBAC、PostgreSQL、私网执行网关、不可篡改审计和真实事故评测。

## 3. 5 分钟讲解顺序

```text
业务问题
→ 为什么普通聊天机器人不够
→ 告警去重和 Agent Run
→ 证据、假设、建议分离
→ Hybrid RAG 和数据权威度
→ Runbook、审批、验证、回滚
→ 降级与安全边界
→ 测试、部署和当前不足
→ 生产化路线
```

不要一开始就罗列 FastAPI、SQLite、DeepSeek。面试官首先关心为什么需要这个系统以及架构如何控制风险。

## 4. 最重要的六个设计点

### 4.1 Agent Run，而不是一次问答

一次事故会经历多个工具调用、审批和状态变化，因此必须有持久化运行实体。`AgentRun` 保存输入、证据、假设、Runbook、审批、执行、验证、回滚和知识候选，可以重放和审计。

### 4.2 证据与推测分离

指标、日志、Trace 和状态更新是 Evidence；“下游依赖异常”是 Hypothesis。模型不能把后者描述成已经证实的事实。

### 4.3 控制面与执行面分离

LLM 负责提出结构化建议，不持有生产凭据。真实执行器必须独立部署在企业私网，并在 API 层执行 RBAC、允许列表和参数校验。

### 4.4 混合检索与权威边界

BM25 保证错误码和术语精确召回，多语言向量解决中英文表达差异，RRF 融合排名。数据源再按权威度重排，外部事故不能直接支持生产动作。

### 4.5 失败可以降级但不能伪造

- DeepSeek 失败：使用确定性规则；
- Wikimedia 在线源失败：使用验证快照；
- 单个遥测工具失败：记录失败，其他调查继续；
- 证据不足：要求补充数据，不给高风险建议。

### 4.6 闭环不是“执行完成”

真正闭环还需要恢复条件验证、失败回滚、人工升级和复盘审核。执行成功的 HTTP 返回值不能证明业务已经恢复。

## 5. 架构类面试问答

### Q1：为什么要做 OnCall Agent？

答：值班故障调查高度依赖跨平台信息聚合，重复操作多，MTTA 和 MTTR 受人工经验影响。Agent 适合把告警去重、证据收集、Runbook 检索和复盘整理自动化，但高风险决策仍需要策略和人工控制。

### Q2：它和普通 RAG 客服有什么区别？

答：普通 RAG 主要是“问题—检索—回答”；本项目有告警入口、工具调用、事故状态机、审批、执行演练、恢复验证、回滚和知识审核。RAG 只是其中的知识支撑模块。

### Q3：为什么使用 FastAPI？

答：项目需要 Pydantic 对外部告警、模型输出和工具响应做严格类型校验；同时需要异步并行访问状态页、遥测网关和模型 API。FastAPI 能直接复用类型生成 OpenAPI，适合控制面原型。

### Q4：为什么前端不用 React/Vue？

答：公开项目优先考虑零构建依赖和 GitHub Pages 部署，因此选择原生 SPA。代价是组件复用、类型安全、状态管理和 E2E 工程能力较弱。生产版本会考虑 TypeScript + React/Vue，并引入组件测试。

### Q5：为什么不做成一个大 Agent 自己决定所有工具？

答：事故响应属于高风险场景。开放式工具选择会扩大权限和不可预测路径。本项目固定工具集合、参数边界和阶段顺序，让每步输入输出可测试。未来可以增加动态路由，但工具注册和授权仍必须由服务端控制。

### Q6：为什么控制面与执行面必须分离？

答：提示词不能作为安全边界。即使模型被提示词注入，独立执行网关仍能根据调用者身份、资源允许列表、参数范围和变更策略拒绝操作。

### Q7：系统如何扩展到多服务？

答：引入服务目录和 CMDB，将告警映射到服务、环境、团队、依赖拓扑和可用 Runbook；工具网关根据服务身份路由到对应遥测后端；执行权限按服务和环境隔离。

### Q8：如果告警量突然增加怎么办？

答：当前单实例内存限流不足。生产设计需要 Alertmanager 分组与抑制、消息队列削峰、按 fingerprint 幂等消费、异步 Worker、Redis 分布式限流，并为严重等级设置优先队列。

### Q9：为什么当前 SQLite 不适合生产？

答：SQLite 适合单进程演示，但多实例写竞争、水平扩展、细粒度权限、高可用和审计能力不足。生产应迁移 PostgreSQL，并通过事务和唯一约束保证状态机与去重一致性。

### Q10：为什么需要消息队列？

答：遥测查询和模型推理可能耗时，不能让告警 Webhook 长时间阻塞。入口应先完成认证、校验、去重和持久化，再把调查任务放入队列，由 Worker 重试和执行。

## 6. 告警与可靠性问答

### Q11：如何避免重复告警创建多个事故？

答：优先使用上游 fingerprint；没有时，对来源、环境、服务、标题和排序标签计算确定性哈希。SQLite 以 fingerprint 为主键，冲突时更新次数和状态，不新建 Agent Run。

### Q12：当前去重有什么不足？

答：没有去重过期窗口、告警聚合规则和跨实例事务。相同 fingerprint 可能永久复用。生产需要定义告警生命周期、恢复后重新触发规则和数据库唯一约束。

### Q13：Webhook 如何保证可靠投递？

答：当前返回 `202 Accepted` 并持久化告警。生产需要快速响应、幂等键、上游重试、死信队列和消费状态。不能依赖一次 HTTP 请求完成整个调查。

### Q14：如果一个遥测工具超时怎么办？

答：四个只读工具并行执行，每个请求有超时；失败会形成 `failed` ToolCall，其他结果继续进入分析。系统必须明确标记证据缺失，不能生成假数据补齐。

### Q15：如何判断事故已经恢复？

答：不能只判断执行接口成功。Runbook 必须定义恢复条件，例如错误率、P95 延迟、积压量、实例健康和持续观察窗口。系统重新查询只读遥测，满足条件才转为 Recovered，否则回滚或升级。

### Q16：如何保证回滚可靠？

答：回滚动作需要版本化、预验证和与正向操作同等级的权限控制。执行前保存原状态和变更 ID，执行后再次验证。当前项目只模拟回滚流程，没有生产级证明。

## 7. LLM 与 Agent 问答

### Q17：LLM 在系统中负责什么？

答：负责基于给定证据生成结构化根因假设、验证步骤、建议和回滚说明。它不负责认证、授权、持久化、参数边界和最终执行。

### Q18：如何降低幻觉？

答：限制输入证据、要求引用证据 ID、结构化输出校验、证据不足时降级、RAG 引用、服务端策略重检，并把结论称为“假设”而不是“已确认根因”。

### Q19：为什么还要规则引擎？

答：规则引擎提供确定性降级、可测试基线和安全兜底。模型不可用或输出无效时，系统仍能完成证据整理和保守建议。规则也用于判断 LLM 是否真正带来增益。

### Q20：置信度代表什么？

答：当前是根据关键词命中和证据数量计算的排序启发式，不是概率，也没有校准。生产评测后才能通过可靠性图、Brier Score 或温度缩放等方法讨论校准。

### Q21：如何防止 Prompt Injection？

答：外部文档只作为数据，不执行其中指令；工具和 URL 由服务端允许列表定义；模型不持有凭据；输出通过结构化 Schema 和策略层；生产还需文档信任分层、内容扫描、敏感字段过滤和对抗测试。

### Q22：为什么不能仅靠 System Prompt 禁止危险操作？

答：Prompt 是行为引导，不是权限控制。模型可能受恶意文档、用户输入、工具返回或模型错误影响。真正限制必须放在执行 API 的身份认证、RBAC、资源范围和参数验证中。

### Q23：如何评估根因分析质量？

答：构建带最终复盘标签的历史事故集，按事故发生时间截断证据，避免未来信息泄漏；统计 Top-1/Top-3 根因命中率、证据引用正确率、无答案识别率、建议安全率和调查耗时，并按服务和故障类型分层报告。

### Q24：为什么公开事故回放只给早期时间线？

答：如果把事故最终根因提前放进输入，评测会发生标签泄漏。系统只提供前几条公开更新，让 Agent 在接近真实事故早期的条件下生成假设。

## 8. RAG 面试问答

### Q25：为什么选择 Hybrid RAG？

答：事故知识同时包含精确错误码和自然语言描述。BM25 擅长精确术语，多语言向量擅长跨语言语义，二者互补。

### Q26：为什么使用 RRF？

答：BM25 分数和向量相似度不在同一量纲，直接线性相加需要复杂归一化。RRF 只依赖各通道排名，对分数尺度更稳健，也容易解释。

### Q27：RRF 如何计算？

答：一个文档在每个召回列表中的贡献为 `weight / (k + rank)`，然后跨通道求和。本项目还把数据源权威度和问题意图路由权重乘入融合分数。

### Q28：为什么要设置命名空间？

答：Runbook、历史事故、实时状态、组件官方文档和外部复盘具有不同用途和权威度。如果放在同一池中等权检索，外部公司的操作可能被错误迁移到当前企业。

### Q29：如何处理中文问题检索英文文档？

答：词法通道提取中文连续片段、中文二元组和拉丁术语；语义通道使用多语言嵌入模型。融合后保留每个引用来自哪个通道。

### Q30：如何分块？

答：约 900 字符一个块、120 字符重叠，并优先在段落或中文句号截断。块太小会丢失上下文，太大会降低检索精度并增加 Token 成本。

### Q31：如何评估检索？

答：准备问题—相关文档—相关片段标注，统计 Recall@K、MRR、nDCG、引用覆盖率和错误来源率；分别评估 BM25、向量和融合结果，再做消融实验。

### Q32：为什么目前不使用独立向量数据库？

答：公开数据规模只有几十份文档，进程内索引足以验证算法，减少部署复杂度。生产数据扩大、需要多实例和增量更新时再迁移 pgvector、Qdrant 或 Milvus。

### Q33：用户上传文档安全吗？

答：当前限制文件类型、大小和文本长度，不执行文档内容。但文档会进入模型上下文，仍可能包含恶意提示或敏感数据。生产需要病毒扫描、内容分类、权限隔离、租户过滤和数据保留策略。

## 9. 会话记忆问答

### Q34：上下文为什么使用摘要加剪切？

答：只保留全部原文会无限增加 Token 和延迟；只保留摘要会丢失近期细节。因此使用滚动摘要保存早期信息、最近 8 条保留原文、总字符预算硬截断。

### Q35：摘要能作为事实证据吗？

答：不能。摘要可能丢失或改写信息，只用于保持对话连续性。事故事实必须来自检索引用或遥测证据。

### Q36：当前记忆有什么问题？

答：存储在进程内，服务重启丢失；没有用户鉴权和租户隔离；摘要是确定性文本压缩。生产需要按用户和事故隔离的持久化记忆，并设置 TTL 和数据删除策略。

## 10. 安全与生产问答

### Q37：当前可以接生产吗？

答：可以接入只读影子模式，不能开放生产写权限。当前缺少 SSO/RBAC、真实审批身份、HMAC 防重放、私网执行网关、PostgreSQL 和不可篡改审计。

### Q38：当前最严重的安全问题是什么？

答：审批和执行演练接口没有用户认证，审批者名称由客户端提交。虽然当前只执行 Dry Run，但如果直接替换为生产执行器会形成严重越权风险。

### Q39：生产执行器应该怎么设计？

答：单独部署在私网；使用短期身份凭据和 mTLS；只暴露版本化动作，不提供通用 Shell；每个动作定义资源允许列表、参数 Schema、风险等级、幂等键、超时、验证和回滚。

### Q40：哪些动作可以逐步自动化？

答：低风险、可逆、影响范围小、Runbook 稳定的动作，例如单个无状态实例滚动重启、有限扩容、已审核功能开关。数据库迁移、数据删除、权限变更和全局流量切换保留人工审批。

### Q41：如何设计审批？

答：审批必须绑定真实身份、角色、资源范围、计划版本和参数摘要；高风险动作支持双人审批；审批后任何计划变化都使原审批失效；所有记录写入不可篡改审计。

### Q42：为什么 CORS 不是鉴权？

答：CORS 只限制浏览器跨域读取，无法阻止服务端脚本或直接 HTTP 请求。生产接口仍必须使用身份认证和授权。

### Q43：为什么静态 Webhook Token 不够？

答：静态 Token 泄漏后可长期伪造请求，也不能阻止合法请求被重放。生产应使用 HMAC 签名、时间戳、随机数、短时窗口和密钥轮换，或者使用 mTLS/OAuth2 工作负载身份。

## 11. 数据库与并发问答

### Q44：多实例下如何保证只创建一个事故？

答：在 PostgreSQL 对 `(tenant_id, fingerprint, lifecycle_window)` 建唯一约束；事务中使用 `INSERT ... ON CONFLICT`；只有首次插入的消费者发布调查任务。不能依赖进程锁。

### Q45：如何保证状态机一致性？

答：更新时校验当前状态和版本号，使用乐观锁或条件更新，例如 `UPDATE ... WHERE status='awaiting-approval' AND version=?`。执行任务使用幂等键，防止重试导致重复操作。

### Q46：如何保存审计日志？

答：业务表保存最新状态，追加式事件表保存每次状态变化、调用者、计划摘要和哈希；再异步写入不可修改的对象存储或审计系统。普通 SQLite 行记录不满足高等级审计要求。

### Q47：如何处理长时间任务？

答：API 只创建任务并返回 Run ID；Worker 从队列执行工具和模型调用；状态通过数据库、轮询、SSE 或 WebSocket 更新；任务有超时、重试、取消和死信状态。

## 12. 测试问答

### Q48：现在测试了什么？

答：30 项测试覆盖数据源映射、降级、RAG、DeepSeek 输出、安全阻断、遥测网关、告警去重、审批、演练、恢复验证、回滚、知识审核和 API 流程。

### Q49：测试还缺什么？

答：缺少真实企业事故评测、负载测试、长稳测试、Chaos、浏览器 E2E、SAST/DAST、依赖扫描和真实执行器集成测试。

### Q50：如何测试模型输出？

答：单元测试使用 Mock Transport 固定模型响应，验证 JSON Schema、证据引用和安全策略；离线评测使用固定事故集；线上采用 Shadow Traffic，不直接验证生产写操作。

### Q51：如何防止评测数据泄漏？

答：按事故时间切分，只允许使用根因公布前的数据；历史复盘中的最终根因不能出现在 Agent 输入；训练/调参事故与最终测试事故分离。

## 13. 性能与成本问答

### Q52：延迟主要在哪里？

答：外部状态源、四路遥测、向量首次生成和 LLM 推理。优化方式包括并行工具调用、缓存、预计算嵌入、缩小上下文、模型超时和异步任务。

### Q53：为什么首次检索更慢？

答：文档同步时只建立文本分块，向量在首次搜索时懒生成。这样避免启动和首屏阻塞，但把成本转移到第一次查询。生产可在后台预热或增量计算。

### Q54：如何控制模型成本？

答：限制证据和引用数量、上下文预算、输出 Token、缓存公共知识、先使用规则分流、对低风险固定问题使用模板，并记录每次 TokenUsage。

### Q55：如何容量规划？

答：分别估算告警峰值、每事故工具调用数、模型并发、平均上下文、知识分块数和保留周期。高严重等级使用独立优先队列，避免普通告警耗尽模型额度。

## 14. 场景题回答模板

### 场景一：错误率突然升高

```text
1. 确认告警窗口、服务、环境和影响范围；
2. 去重并关联同一时间的其他告警；
3. 查询错误率、延迟、饱和度和请求量；
4. 查询异常日志与失败 Trace；
5. 读取近期发布、配置和依赖变更；
6. 形成多个可证伪假设，而不是直接下结论；
7. 匹配 Runbook 和历史事故；
8. 选择最小影响动作并说明验证与回滚；
9. 高风险动作人工审批；
10. 验证业务指标恢复并生成复盘。
```

### 场景二：模型不可用

答：告警、工具查询和状态机继续工作；根因分析退回确定性规则；界面明确标记降级；不伪造 LLM 结果；必要时升级人工。

### 场景三：日志系统不可用

答：记录日志工具失败，继续使用指标、Trace 和变更；降低结论置信度；要求人工补充证据；禁止因单一数据源缺失执行高风险操作。

### 场景四：Agent 建议重启全部实例

答：策略层拒绝通用高影响动作。只能匹配审核后的滚动重启 Runbook，限制目标比例和并发，先 Canary，验证错误率和容量，再逐步扩大；失败立即停止和回滚。

### 场景五：恶意 Runbook 要求上传密钥

答：文档只作为不可信数据；检索结果不能改变系统指令；工具不提供读取密钥能力；执行网关拒绝不在允许列表的动作；记录安全事件并隔离文档。

## 15. 技术取舍表

| 选择 | 优点 | 缺点 | 何时替换 |
|---|---|---|---|
| FastAPI | 类型清晰、异步方便 | CPU 密集型需外部 Worker | 大规模任务引入队列与 Worker |
| SQLite | 简单、演示成本低 | 单实例、高可用弱 | 生产迁移 PostgreSQL |
| 原生 SPA | 无构建、Pages 简单 | 组件化和类型弱 | 团队协作时迁移 TypeScript |
| 进程内向量 | 小数据快 | 多实例不共享 | 文档扩大后迁移 pgvector/Qdrant |
| 固定工具 | 安全、可测试 | 灵活性有限 | 企业工具注册中心成熟后动态路由 |
| 规则 + LLM | 有降级和基线 | 维护两条路径 | 不建议完全删除规则 |
| 人工审批 | 风险低 | 自动化率下降 | 仅对经过验证的低风险动作免审批 |

## 16. 面试中容易说错的话

| 错误说法 | 正确说法 |
|---|---|
| “置信度 90% 就代表根因正确率 90%” | 当前置信度是未校准的排序启发式 |
| “系统已经自动修复生产故障” | 当前只执行安全演练，生产执行器尚未接入 |
| “用了 RAG 就不会幻觉” | RAG 降低无依据回答，但仍需引用校验和安全策略 |
| “CORS 已经保护接口” | CORS 不是身份认证 |
| “外部事故越多越好” | 数据必须按企业、组件、版本和权威度分层 |
| “模型自己决定工具更智能” | 高风险场景先保证最小权限和可审计性 |
| “SQLite 足够生产使用” | 当前单实例可用，生产高可用需迁移 |
| “Runbook 匹配后可以直接执行” | 还要授权、参数校验、审批、验证和回滚 |

## 17. STAR 项目表达

### Situation

值班人员面对重复告警，需要在多个工具之间手工聚合证据，根因判断依赖个人经验，事故过程难以标准化沉淀。

### Task

实现一个可演示、可审计且不冒充生产自动化的 OnCall Agent，覆盖告警到复盘的完整闭环，并使用真实公开事故验证流程。

### Action

- 设计告警去重与 Agent Run 状态机；
- 分离证据、假设、建议和执行；
- 实现固定只读遥测网关；
- 设计 BM25 + 多语言向量 + RRF 的分层 RAG；
- 引入 Runbook、人工审批、恢复验证和回滚；
- 使用 DeepSeek，同时保留规则降级；
- 接入 Wikimedia 真实事故和 Runbook；
- 完成 Railway、GitHub Pages 和自动化测试。

### Result

形成了一个可以在线演示的事故控制面原型，30 项测试覆盖核心闭环；系统能展示真实事故、启动调查、生成证据约束假设、进入审批和演练，并明确标注生产化阻塞项。

不要虚构 MTTR 降低比例或企业生产事故数量。没有真实实验数据时回答“尚未完成企业影子模式评测”。

```text
取舍：牺牲了什么。

```

示例：

> 我使用 RRF 融合 BM25 和向量排名，因为二者分数尺度不同，直接加权需要额外校准。实现中先独立召回候选，再按倒数排名、来源权威度和问题意图计算融合分数。代价是 RRF 不利用原始分数差距。数据规模扩大后，我会用标注集学习融合权重并比较 nDCG 和 Recall@K。
