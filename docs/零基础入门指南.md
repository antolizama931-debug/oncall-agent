# OnCall Agent 零基础入门指南

> 这份文档写给第一次接触运维、后端和 AI Agent 的读者。你不需要先懂专业术语。必须使用的术语会先用日常语言解释，再给出正式名称。

## 1. 先用一句人话理解这个项目

OnCall Agent 是一个“帮助技术人员处理线上故障的智能助手”。

例如，一家网站突然打不开了。以前需要值班人员手工完成下面这些事情：

1. 看到异常通知，确认到底出了什么问题；
2. 查看系统运行数字和错误记录；
3. 判断最可能的原因；
4. 查找公司以前处理类似问题的方法；
5. 提出修复建议；
6. 高风险操作先让人批准；
7. 修复后确认网站是否恢复；
8. 把本次故障记录下来，方便下次使用。

本项目把这套重复流程做成一个可以记录、检查和回放的程序。它的目标是让故障发现得更快、原因查得更快、处理过程更规范。

## 2. 它不是万能机器人

当前公开版本是一个安全演示版，主要展示“怎样调查和控制故障处理流程”。它可以读取公开事故、接收测试告警、分析原因、匹配处理手册、模拟审批与修复流程，但不会真的重启企业服务器或修改生产数据库。

原因很简单：让 AI 随意控制真实服务器非常危险。真正接入企业生产环境前，还需要企业账号体系、权限控制、内部监控接口、安全审计和经过验证的修复工具。

可以把当前版本理解为“驾驶训练场”，而不是已经在公共道路上无人驾驶的汽车。

## 3. 用一个例子看懂完整流程

假设某个网站的错误率突然升高。

### 第一步：收到告警

监控系统发现错误率超过规定范围，向 OnCall Agent 发来一条消息。

“告警”就是系统自动发出的异常通知，例如“网页错误率超过 5%”或“数据库连接失败”。

### 第二步：合并重复通知

同一个问题可能一分钟内连续发来几十条通知。系统会判断它们是否属于同一件事，避免建立几十个重复事故。这个过程叫“告警去重”。

### 第三步：收集线索

系统会查看四类常见线索：

- 指标：CPU 使用率、错误率、请求时间等数字；
- 日志：程序运行时写下的事件和错误文字；
- 调用链：一次请求经过了哪些服务、在哪一步变慢或失败；
- 变更：故障前是否刚发布新版本、修改配置或切换数据库。

这些能被实际查看和引用的内容统称为“证据”。

### 第四步：提出可能原因

系统根据证据提出一个或多个可能原因，例如新版本存在错误、下游服务不可用、数据库连接数已经用完。

这些还没有完全证实的判断叫“根因假设”。项目会明确区分“看到了什么”和“猜测是什么”，避免把猜测冒充事实。

### 第五步：查找以前的处理方法

系统从事故复盘、操作手册和技术文档中查找相似情况，找到经过审核的处理步骤。

这种“先查资料，再让模型回答”的方法叫 RAG。你暂时只要记住：它让 AI 尽量根据项目资料回答，而不是只靠自己的记忆猜答案。

### 第六步：给出处理建议

例如，系统建议“先把 10% 的流量切回旧版本，再观察五分钟错误率”。建议必须来自允许执行的操作手册，而不是让大模型临时编一条危险命令。

这类写明检查步骤、处理步骤和恢复条件的手册叫 Runbook，可以理解为“故障处理说明书”。

### 第七步：判断是否需要人工批准

只读查询风险很低，可以自动完成；重启服务、回滚版本、修改流量等动作会影响线上系统，需要按风险决定是否让人批准。

这个检查点叫“策略门控”，意思是系统先按规则检查权限和风险，再决定继续、等待批准或直接阻止。

### 第八步：验证结果

执行动作不等于问题已经解决。系统还要再次查看错误率、请求时间和服务状态，确认业务真的恢复。若没有恢复，则进入回滚或通知人工处理。

### 第九步：沉淀经验

系统生成本次事故的时间线、证据、判断、操作和结果，交给人工审核。审核通过后才加入正式知识库，防止错误经验污染以后回答。

## 4. 页面分别有什么用

### 导航首页

这是项目介绍页，帮助访客快速理解项目解决什么问题、使用什么真实数据、有哪些安全限制，并提供进入工作台的按钮。

### 事故控制台

它相当于值班人员的工作总览。可以查看事故、打开某个事故开始调查、查看哪些建议等待批准，以及查看修复验证、回滚和复盘状态。

它不是多余页面。聊天页面适合问一个问题，而事故控制台适合管理一整件持续变化的故障。

### 事故调查页

展示某次事故的原始信息和时间线，并允许启动一次完整调查。

### 运行回放页

展示系统这一次做了什么、查了哪些数据、为什么得出这个判断、是否需要审批以及最终结果。它让每一步都能被检查，而不是只看到一句 AI 答案。

### 知识问答工作台

这里可以上传 PDF、Markdown 或 TXT 文档并提问。回答会显示引用来源，也会保留本次会话的近期内容。

## 5. 知识库到底存在哪里

当前项目主要使用两个 SQLite 文件。SQLite 可以理解为“保存在单个文件里的小型数据库”，很适合演示和单机运行。

- `data/knowledge.db`：保存上传文档中提取出的文字、文档信息和分段内容；原始 PDF 文件本身不长期保存；
- `data/runtime.db`：保存告警、事故调查过程、审批、执行演练、验证结果和会话状态。

检索时，程序会在应用进程中建立文字索引和向量索引。当前没有使用 Milvus、Qdrant 或 Chroma 这类独立向量数据库。

这套方案适合当前演示版。若进入大企业生产环境，应考虑 PostgreSQL、专门的向量检索能力、对象存储、备份和多副本部署。

## 6. RAG 为什么使用两种查找方式

项目不是只使用 BM25，而是把两种方法结合起来。

### BM25：适合查“原词”

BM25 是一种文字匹配算法。它擅长查错误码、服务名、命令和原文中的准确词语。例如搜索 `HTTP 503`，很容易找到同样包含 `HTTP 503` 的段落。

### 向量检索：适合查“意思相近”

向量检索会把一段话转换成一组数字，用这些数字比较两段话在含义上是否接近。例如用户问“网站访问很慢”，英文文档写的是“high request latency”，虽然文字不同，仍有机会被找到。

### RRF：合并两份搜索结果

BM25 和向量检索各自会得到一份排名。RRF 是一种合并排名的方法，让两边都排得靠前的内容优先出现。

```text
用户问题
→ 精确文字查找
→ 相近意思查找
→ 合并两边结果
→ 按资料可信程度再次排序
→ DeepSeek 根据找到的资料生成回答
→ 显示引用来源
```

这就是项目所说的“混合检索 RAG”。

## 7. Agent 又是什么意思

普通问答程序通常只做一次“问题进去、答案出来”。Agent 会为了完成目标分步骤工作：决定下一步、调用工具、查看结果，再决定后续动作。

本项目中的 Agent 不允许无限自由行动。它只能调用事先登记的工具，每次运行有最大步骤数，高风险建议必须经过规则和人工批准。

因此它更像“按照工作制度办事的智能值班助手”，而不是“可以任意控制电脑的 AI”。

## 8. 会话记忆是怎么做的

如果把所有历史对话都交给模型，内容会越来越长、越来越慢、费用也会增加。本项目采用两层办法：

- 保留最近几轮原话，避免丢失当前问题的细节；
- 把更早的对话压缩成摘要，只保留重要背景。

这就是“摘要加剪切”。摘要用于保持对话连贯，但不能当作事故事实证据；真正的结论仍必须引用日志、指标、事故记录或文档。

## 9. 项目中的真实数据是什么

项目主要使用 Wikimedia 公开的服务状态、事故复盘和故障处理手册作为主领域资料。Wikimedia 是维基百科等网站背后的组织，其公开资料包含真实的大型互联网系统运维经验。

项目还可以把 Kubernetes、Prometheus、MariaDB 等官方技术文档作为补充资料，并把其他企业公开复盘作为低权重参考。不同企业的环境不一样，因此外部案例只能帮助分析，不能直接证明某个生产操作适合当前企业。

## 10. 代码目录怎么读

第一次看代码时按下面顺序即可：

1. `app/main.py`：程序入口和网页接口，可以理解为“总接待台”；
2. `app/alerts.py`：接收告警、整理告警并处理重复通知；
3. `app/engine.py`：事故调查和判断的核心流程；
4. `app/connectors.py`：统一连接外部监控、日志等工具；
5. `app/automation.py`：审批、执行演练、验证、回滚和知识沉淀；
6. `app/knowledge.py`：文档解析、搜索和知识问答；
7. `app/deepseek.py`：调用 DeepSeek，并处理调用失败；
8. `app/runtime.py`：保存事故运行记录；
9. `frontend/`：用户看到的网页；
10. `tests/`：自动检查代码行为是否符合预期。

不要试图第一天读完所有代码。先沿着“一条告警如何变成一次调查”这条主线阅读。

## 12. 第一次如何实际体验

1. 打开导航首页，先看项目定位和安全边界；
2. 进入事故控制台，选择一个 Wikimedia 真实事故；
3. 打开事故，阅读中文时间线；
4. 启动调查，观察系统收集的证据和可能原因；
5. 查看为什么建议被允许、等待批准或阻止；
6. 运行安全演练，查看恢复验证或失败回滚分支；
7. 打开知识问答工作台，询问“这次事故最可能的原因是什么”；
8. 检查回答是否给出引用，而不是只看答案是否流畅。

## 13. 零基础面试介绍模板

### 30 秒版本

> 我做的是一个线上故障处理助手。它接收并合并重复告警，自动收集日志、指标和变更记录，再结合历史事故和处理手册判断可能原因。高风险操作不会由 AI 直接执行，而要经过规则检查和人工批准；处理后还会验证是否恢复，并把本次经验交给人工审核后加入知识库。当前公开版完成了整个安全演练流程，还没有直接获得企业生产写权限。

### 被问“项目亮点是什么”

> 第一，系统不是只回答问题，而是管理从告警到复盘的完整流程；第二，它把真实证据和模型推测分开，并为结论保留引用；第三，它使用关键词和语义两种检索方式，既能查错误码，也能处理中英文不同表达；第四，高风险动作经过策略和人工审批，执行后必须验证，失败则回滚或交给人工。

### 被问“能直接接生产吗”

> 目前不能直接无人值守接管生产。当前版本适合演示、事故回放和只读影子模式。进入生产前还需要企业登录与权限控制、内部监控和日志连接器、生产级数据库、私网执行器、不可篡改审计、双人审批以及真实历史事故评测。我会先让系统只读观察并与人工结论对比，再逐步开放低风险动作。

## 14. 推荐学习顺序

- 第一天：只读第 1～4 节并实际打开一次事故，能用自己的话说清楚项目用途；
- 第二天：复习第 3、8、12 节，能说清楚告警到复盘的完整流程；
- 第三天：学习第 5～6 节，能解释为什么需要两种搜索；
- 第四天：按第 10 节顺序跟踪一次请求，不追求看懂每一行；
- 第五天以后：再阅读《项目技术说明书》和《大厂面试速查手册》。

## 15. 最后只记住五句话

1. 这个项目帮助技术人员更快、更规范地处理线上故障。
2. 它先收集真实线索，再提出可能原因，不把猜测说成事实。
3. 它会查历史事故和处理手册，并为回答保留来源。
4. 高风险操作必须受规则和人工控制，执行后还要验证和回滚。
5. 当前公开版是安全演练和控制流程原型，不是已经无人值守接管生产的系统。
