# 5 分钟看懂 OnCall Agent

如果你第一次接触运维和 AI，只读这份文档即可。

## 1. 这个项目做什么

网站、数据库或接口发生故障时，技术人员通常需要：

1. 接收异常通知；
2. 查看错误记录和运行数据；
3. 判断可能原因；
4. 查找以前的处理方法；
5. 决定是否执行修复；
6. 检查系统是否恢复；
7. 保存本次处理记录。

OnCall Agent 把这些步骤放进一个统一流程，减少重复查找和手工整理工作。

## 2. 用一个故障理解它

假设某个网站突然出现大量 `HTTP 500` 错误。

| 系统步骤 | 它实际做的事 |
|---|---|
| 收到告警 | 接收“错误率过高”的通知 |
| 合并告警 | 把同一故障的重复通知合并 |
| 收集证据 | 查看错误日志、请求耗时和最近发布记录 |
| 判断原因 | 提出“新版本可能有问题”等待验证的判断 |
| 查找方案 | 从历史事故和处理手册中找到相关步骤 |
| 风险检查 | 只读查询可以继续，重启或回滚需要人工批准 |
| 验证恢复 | 再次检查错误率是否下降 |
| 保存记录 | 生成人工审核后的事故总结 |

最重要的原则：**系统看到的证据和 AI 提出的可能原因必须分开。**

## 3. 现在已经能做什么

- 读取 Wikimedia 公开发布的真实事故；
- 接收测试告警并合并重复告警；
- 按步骤生成一次完整调查；
- 查询公开事故记录和处理文档；
- 给出带来源的回答；
- 展示人工审批、修复演练、恢复检查和失败回滚；
- 保存每一步操作，便于检查和回放。

## 4. 现在不能做什么

- 不能直接读取某家企业的内部日志和监控数据；
- 不能直接重启真实服务器、修改数据库或切换生产流量；
- 不能保证 AI 提出的原因一定正确；
- 不能代替企业的账号、权限、审计和安全系统。

因此，当前公开版本是**安全演示和事故调查原型**，不是已经接管生产环境的无人值守系统。

## 5. 为什么需要 AI

AI 主要负责两件事：

1. 整理多条故障信息，提出需要继续验证的可能原因；
2. 根据检索到的资料生成容易阅读的回答。

AI 不负责绕过权限，也不能直接生成并执行任意生产命令。高风险动作必须经过固定规则和人工批准。

## 6. 为什么回答会带资料来源

程序会先查找事故记录和处理文档，再让 DeepSeek 根据查到的内容回答。这种方式叫检索增强生成（RAG）。

项目同时使用：

- **关键词查找**：适合错误码、服务名和命令；
- **意思相近查找**：适合用户问题与文档用词不同的情况。

两种结果合并后，可信来源排在前面。回答仍然可能有误，所以页面会保留原始链接供人工核对。

## 7. 页面怎么使用

| 页面 | 用途 |
|---|---|
| 导航首页 | 了解项目和进入其他页面 |
| 事故控制台 | 查看事故、待批准任务和处理状态 |
| 事故调查页 | 查看某次事故并启动调查 |
| 运行回放页 | 检查系统每一步做了什么、依据是什么 |
| 知识问答页 | 上传文档并进行带来源的问答 |

## 8. 第一次体验只做四步

1. 打开[项目演示](https://antolizama931-debug.github.io/oncall-agent/)；
2. 进入“事故控制台”，选择一条事故；
3. 点击“开始调查”，查看证据和可能原因；
4. 打开“知识问答”，提问并检查回答引用的资料。

如果页面只能展示事故、无法生成新回答，通常表示 Railway 后端正在休眠或暂时不可访问，不代表前端页面损坏。

## 9. 只需要认识八个词

| 词语 | 简单含义 |
|---|---|
| 告警（Alert） | 系统自动发出的异常通知 |
| 事故（Incident） | 一次影响服务正常运行的问题 |
| 日志（Log） | 程序记录的运行信息和错误文字 |
| 指标（Metric） | 错误率、CPU 使用率等运行数字 |
| 根因（Root Cause） | 真正导致故障发生的原因 |
| 处理手册（Runbook） | 经过审核的检查和修复步骤 |
| 智能体（Agent） | 能按步骤调用工具完成任务的程序 |
| 检索增强生成（RAG） | 先查资料，再根据资料生成回答 |

## 10. 面试时怎么介绍

> 我实现了一个 OnCall Agent，用于规范线上故障从告警接入到复盘的处理流程。系统会合并重复告警，收集证据，查询历史事故和处理手册，再给出带来源的可能原因。高风险操作必须经过规则和人工审批，执行后还要验证恢复；当前公开版只进行安全演练，不直接操作企业生产系统。
